# Statements

If expressions are the logic of the `invariants` DSL, **statements** are the scaffolding. Statements do not evaluate to a value, nor do they return anything. Their sole purpose is to declare contracts, bind scope, and instruct the syntax oracle on _when_ to execute an expression (ie; defining the semantic anchors).

## 1. Specification Declarations (`spec`)

A `spec` is the highest-level declaration in the AST. It binds a name to a block of rules. It is effectively the DSL's equivalent of a `class` or `struct`.

```
spec BulkOrder { ... }
```

When the syntax oracle enters a `spec`, it initializes the semantic dependency graph ($E_{sem}$) for that scope.

## 2. Field Declarations (`field`)

A `field` block maps directly to a key in the downstream JSON schema. It is a refinement type wrapper that limits the scope of any internal expressions exclusively to the field's `value`.

```
field quantity: integer { ... }
```

Fields represent **context-free** anchors. The syntactic module ($M_{syn}$) validates these rules the moment the LLM completes the field's token generation.

## 3. Constraints

Constraint statements exist inside both `field` and `invariant` blocks. They evaluate to a boolean expression.

```
this.value >= 1;
```

_Note:_ Multiple constraints within a single field implicitly act as a logical `AND`. If any constraint evaluates to `false`, the field/invariant is rejected.

## 4. Invariant Declarations (`invariant`)

An `invariant` operates at the `spec` level. It declares a **context-sensitive** rule that requires access to multiple fields simultaneously.

```
invariant bulk_discount {
    this.quantity > 500 -> this.total_price < (this.unit_price * this.quantity);
}
```

Invariants are evaluated sequentially by the semantic module only when all dependent variables accessed via `this` have been fully generated by the LLM.
